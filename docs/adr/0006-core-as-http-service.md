# ADR-0006: core 作为常驻服务（QUIC/HTTP3），TUI 为独立客户端

- 状态：已接受（QUIC 修正 + 全可靠流修正 2026-08-09）；**传输选择已被 ADR-0026 取代**（2026-10-06，改走 WebSocket）。core 是常驻服务、客户端独立进程这一条不变
- 日期：2026-08-09

## 决策

core 对客户端（TUI/未来 gui）暴露 **QUIC/HTTP3** 接口：core 是常驻服务进程，TUI 是独立客户端进程。REST 语义（`POST /message`、`POST /command`、`POST /approval-response`、`GET /sessions` 等）跑在 HTTP/3 上。**推送流**（事件 + 增量）走 HTTP/3 长生命周期单向流（SSE 语义），可靠有序。

**全可靠流**：所有推送一律可靠，增量与结构化事件无差别——丢弃任何一种都致命（LLM 缺段落、turn_end 丢失断流）。可靠性由 QUIC 可靠流原生保证，**不自建确认机制**。**快握手 + 少校验**：QUIC 0-RTT（重复连接握手与数据同发）。**客户端语言不受 C++ 约束**（ADR-0007）。

**远程部署**：项目后期支持**公网部署**——core 可部署在远程服务器，客户端远程连接。QUIC 的 0-RTT 握手、TLS 加密、多路复用为此前提。本地开发同样走 QUIC（localhost），协议唯一。

## 架构演进历史（重要——未来读者需理解为什么走到这）

这条决策经历了三次改判，每个阶段的理由都值得记录：

1. **最初：C++ 单进程（FTXUI 直接链接 core 库）**——原始方案，单进程内直调。
2. **HTTP 连接（第一次改判）**——引入 HTTP 连接，core 成为服务，TUI 语言解放。动机：语言解放、进程隔离、未来多客户端（gui/web 复用）。
3. **QUIC/HTTP3（第二次改判）**——用户："这个项目不只有本地, 后期会上远程, 所以公网通讯是需要的"。QUIC 为公网场景设计（加密、0-RTT、抗丢包），本地与远程同一协议。
4. **全可靠流（第三次改判，最重要）**——用户质疑："按照我的数据传输方法似乎更像一个TCP? QUIC+HTTP/3的设计真的是对的吗?"

**第三次改判的完整过程**（为什么废弃"分层可靠性"方案）：

- 最初设计：可靠消息走 HTTP/3 流，流式增量走 QUIC 不可靠数据报（RFC 9221）。用户提出**时间戳水位确认 + 捎带发送**机制保证增量最终到达：core 每客户端维护发送队列（帧带独立时间戳），发送循环推进未发帧，已发未确认帧保留，唯一删除路径是客户端回报时间戳水位判过期；不设专门重发定时器，下次任何发送动作捎带发送全部未确认帧；上游结束后最后一次发送清空队列。
- 用户对方案的质疑："这些东西不就是外面一个while(1)吗"、"按照我的数据传输方法似乎更像一个TCP?"——**水位 + 捎带发送本质是 TCP 的累积 ACK + 捎带确认 + RTO 重传**，在不可靠数据报上自建可靠传输 = 重复实现 TCP。
- 进一步拆解：用户坚持"没有两种类型, 丢了哪一种的都很致命——LLM丢了一整个段落用户直接看不懂了；turn_end丢了直接整个事件流都断掉了"。即增量不可丢、事件更不可丢。
- **结论**：全部推送走 QUIC 可靠流（原生可靠有序），废弃数据报 + 水位 + 捎带。增量也在同一流里（可靠流支持流式实时，打字效果不损失）。而"更快的握手, 更少的校验"正是 QUIC 相对 TCP 的核心优势（0-RTT vs TCP+TLS 的 1-RTT + 1-RTT）——**QUIC 的选择被证明是对的，错的是"不可靠数据报 + 自建可靠"这个组合**。

## QUIC 库选型（2026-08-09）

**ngtcp2（QUIC）+ nghttp3（HTTP/3 帧 + QPACK）**——标准 C 组合，完整 RFC 9114/9204，保证 curl --http3 / 未来 web 客户端互操作。Go 侧用 quic-go（事实标准，自 v0.27 支持 RFC 9221 数据报，HTTP/3 成熟）。

选型过程：
- 原定 **msquic**（微软开源，跨平台 C API），后查证：**msquic 是纯 QUIC 传输库，不带 HTTP/3 层**（无 QPACK RFC 9204、无 HTTP/3 帧语义 RFC 9114，feature 列表均为传输层：RFC 9000/9001/9002/9221/9287）。
- 选项对比：msquic + 自建简化 H3（QPACK 静态表 + 字面值，合法不压缩）→ 自研协议代码 + 调试工具确定性打折 + 解析 bug 风险自担；**ngtcp2 + nghttp3（选定）** → 工业实现背书、curl/wireshark/未来 web 客户端无缝。
- 成本评估：HTTP/3 只承载可靠消息（请求-响应模式、头极少），QPACK 压缩收益≈0——选标准组合的代价仅是 API 比 msquic 底层，收益是完整互操作。

## 客户端地位平等（2026-08-09）

TUI 与未来的 **gui 是平等的 QUIC 客户端**，共享 core 的同一接口。gui 虽不在第一版实现，但接口设计必须按多客户端（tui + gui）预留——审批询问、事件流订阅等交互面不做 TUI 特化。

## 后果

- core 需要一个 QUIC/HTTP3 服务模块（~~ngtcp2 + nghttp3~~ → **Cloudflare quiche**，见下）。

## 实况注（2026-08-28）：库最终是 Cloudflare quiche

上面选定的 ngtcp2 + nghttp3 **没有落地**。实际实现用的是 **Cloudflare quiche**（QUIC + HTTP/3 一体，`core/CMakeLists.txt:17-19`），Go 侧仍是 quic-go。

原因：**原定组合的实现满足不了需求。** 换库当时没有单独记 ADR，这条实况注是补记；具体是哪一条不满足未留下记录。

后续 ADR 已在以 quiche 的性质为论据（ADR-0002 的线程模型：「quiche 非线程安全，agent 线程不能直接调推送流」），本条把那个前提落到纸面上。
- **推送流（SSE 语义）为长生命周期单向流**：GET /events 流式响应，事件帧按序写入。
- core 与 TUI 的所有交互走 QUIC/HTTP3 + JSON。
- 单进程的"进程内直调"优势（低延迟、共享内存）让位于接口清晰。
- 权限插件的交互式询问需跨进程：core 经推送流发询问，客户端经 POST /approval-response 回传裁决。
- **出站与入站分离**：core 请求 Provider（DeepSeek）仍用 libcurl（HTTP/1.1 客户端）；QUIC/HTTP3 仅用于 core ↔ 客户端（TUI/gui）通信。
- FTXUI 方案废弃（TUI 选型改为 ADR-0007）。
- **数据报（RFC 9221）首版不使用**——全可靠流模型下无"可丢"内容。未来若出现真正可替换状态（如高频遥测）再引入。
